## 摘要

本项目是一个面向小型多业态企业的智能经营管理系统,以开源办公 SDK **Univer** 为在线表格底座,用在线协同表格替代门店零散的本地 Excel 文件,并在其上构建数据录入、数据大屏、AI 经营分析、AI 文生图海报、登录与角色权限等模块。系统已完成从单一业态(足浴)到多业务泛化(足浴 + 汉庭酒店样板)的演进,设计上可线性扩展至月子会所、酒吧、培训学校等业态。

系统的核心架构决策是 **Approach B(录入与展示分离)**:以 PostgreSQL 作为衍生视图(报表、大屏、AI)的唯一事实源,Univer 仅作录入面,从而根治 Excel 跨表公式的脆弱性(`#REF!`/`#DIV/0!`)与跨表重复录入。在此之上,系统提出若干工程创新,其中最具学术价值的是 **以 AI 语义抽取作为唯一数据入库路径**,用大语言模型按表头文字语义对齐字段,取代脆弱的位置式单元格坐标映射。

本文档系统梳理项目的问题动机、总体架构、十项核心创新点、工程实现现状(含已落地与未启用之分)、可作为学术论文贡献的提炼,以及论文写作的忠实性注意事项。

## 一、项目概述

本项目是一个面向小型多业态企业的**智能经营管理系统**,以开源办公 SDK **Univer** 为在线表格底座,用在线协同表格替代门店零散的本地 Excel 文件,并在其上构建数据录入、数据大屏、AI 经营分析、AI 文生图海报、登录与角色权限等模块。系统已完成从单一业态(足浴)到**多业务泛化**(足浴 + 汉庭酒店样板)的演进,设计上可线性扩展至月子会所、酒吧、培训学校等业态。

**技术栈**:

| 层 | 选型 |
|---|---|
| 后端 | Node.js + TypeScript(Express + pg + bcryptjs + JWT + zod + vitest) |
| 数据库 | PostgreSQL(RDS) |
| AI 服务 | 火山引擎豆包(Doubao / Ark),同时承担文本分析与文生图 |
| 前端 | Vue 3 + Vite + Univer Sheets Preset + Tailwind + ECharts + Fabric.js |
| 部署 | 火山 ECS + Nginx + PM2 + Docker PG |

代码同构(TS 前后端),Univer SDK 以 vendor 形式内嵌(`univer-dev/`)。

**代码规模**:后端 `server/src/` 约 30 个 TS 模块 + 19 个测试文件(119+ 测试用例),前端 `web/src/` 约 24 个 Vue/TS 文件,设计文档 `docs/superpowers/specs/` 9 份 + 实现计划 12 份。

## 二、问题与动机

小型企业财务经营长期依赖零散本地 Excel,存在四类痛点(spec `2026-07-17-足浴财务模块-design.md` §1.1、§3.5):

1. **文件分散**--无统一在线底座,跨店/跨期无法汇总;
2. **公式脆弱**--`#REF!`/`#DIV/0!` 类跨表公式,改行列即崩;
3. **跨表重复录入**--资金台账靠经营报表 + 费用明细的跨表公式滚动累加,同一数据填多次;
4. **无法可视化**--无大屏、无 AI 问答。

系统以两条**硬约束**贯穿始终(spec §1.3):

- **可扩展性**:加指标 / 加表 / 加业务 = 改配置,不改代码;
- **低学习成本**:员工操作尽量贴近现有 Excel 工作流,不引入新范式。

---

## 三、总体架构:Approach B(录入与展示分离)

这是本系统最核心的架构决策(spec §2、§14)。系统采用 **方案 B:干净数据底座 + Univer 录入面 + 自动生成报表/大屏**,而 **非** 1:1 复刻 Excel(电子表格本身即事实源)。核心思想是 **录入与展示分离**:员工只在 Univer 录入表填格子,PostgreSQL 是报表/大屏/AI 等衍生视图的**唯一事实源**。

PG 同时存两类数据:① 干净业务表(供大屏、AI 读);② Univer 工作簿快照(供回放与持久化)。报表/台账/大屏/AI 全部从 PG 衍生,从而**根治 Excel 公式脆弱性**并**消除跨表重复录入**(录入归一,enter once)。

详细架构图见[附录 A](#附录-a系统架构图)。

## 四、核心创新点

### 创新点 1:工作表级悲观锁--弃用 Univer Server / OT 的轻量协同

**机制**:系统不使用 Univer Server(其提供 OT 实时协同),改用基于 PG `sheet_lock` 表的工作表级悲观锁 + 自建快照持久化。锁以 `workbook_id + sheet_key` 为键;获取时先清过期再 `INSERT ON CONFLICT DO NOTHING`;心跳续期仅持有者可操作;断线后 TTL 到期自动释放;保存时 `isLockHolder` 所有权校验防覆盖。

**代码佐证**(`server/src/lock/lock.service.ts`):

```ts
// :4-5  锁 TTL 60s,前端每 5s 心跳续约;断线后约 60s 自动过期可被接管
const TTL_MS = 60_000;
// :9-19  acquireLock:先清过期,再 ON CONFLICT DO NOTHING 插入
await query('DELETE FROM sheet_lock WHERE workbook_id=$1 AND sheet_key=$2 AND expires_at < now()', [...]);
const ins = await query(
  `INSERT INTO sheet_lock (...) VALUES (...) ON CONFLICT (workbook_id, sheet_key) DO NOTHING RETURNING *`, [...]);
// workbook.routes.ts:170-171  保存前所有权校验
if (!await isLockHolder(Number(req.params.id), req.user!.id))
  return res.status(409).json({ error: '锁已丢失(被他人接管或过期),保存被拒绝,请重载工作簿' });
```

**为何新颖/可论证**:针对"财务录入是否需要 OT 实时协同"这一前提,系统识别出该场景的并发模型实为 **单编辑者并发**(同一张表同一时间只一人编辑;不同人编辑不同表互不影响,因锁粒度在工作表级)。在此基础上用悲观锁替代 OT,获得三收益:零商业授权风险、部署简单(无额外协同服务进程)、且架构把协同层隔离为可替换点(spec §4.2、§13:"若未来需真实时共编,可再引入 Univer Server,架构已隔离该替换点")。

接管采用 **两阶段礼让机制**:请求方登记 `request_user_id`,持锁者心跳探测到待办请求后 **先自动保存快照再 `yieldLock` 让出**,保证抢占瞬间不丢数据(`Workbook.vue` 心跳分支)。

> ⚠️ **事实校正(论文务必采用真实参数)**:实际 TTL = **60s**、心跳间隔 = **5s**(`lock.service.ts:5`、`Workbook.vue:89` `setInterval(..., 5000)`),非早期文档的"15s 心跳"。接管是 **单槽待办请求(last-requester-wins)**(`schema.sql:112-113` 单字段 `request_user_id`,`requestTakeover` 直接覆盖),并非 FIFO 队列--论文宜表述为"单槽待办接管"。

### 创新点 2:AI 语义抽取作为唯一入库路径(替代位置式 sync)+ 转置表确定性解析

这是本系统 **最具学术价值的创新**。v1 的"录入归一"靠 **位置式 sync**--前端按列下标逐行读单元格写库,有三个硬伤(spec `2026-07-21-AI抽取管线与调度-design.md` §1):

1. **依赖位置**:表头改列/整表转置即 **静默错位漏读**,大屏缺数无报错;
2. **无定时保鲜**:员工忘点"保存并同步"大屏停留在旧数据;
3. **数值校验隐患**:非数字字符串溜进数值键致整个大屏接口 500。

子项目 3 用 **AI 抽取整体替代位置式 sync**:把整张工作表序列化为 TSV 喂给 LLM,由 LLM **按表头文字语义匹配**模板字段后产出结构化 JSON 再写库,`extractForSync`/`/sync`/`sync.service` 全部移除。

**机制与代码**:

```ts
// extraction.service.ts:58  prompt 用 businessName 参数化(去足浴硬编码,适用任意业务)
export function buildMessages(sheet, tsv, businessName = '足浴') {
  const fields = sheet.columns.filter(c => c.kind === 'entry' && c.key !== 'date')
    .map(c => `- ${c.key}=${c.label}`).join('\n');
  const system = `你是${businessName}财务数据抽取助手。从工作表(TSV,第1行表头)识别...`
               + `按表头文字匹配目标字段...严格输出 {"rows":[{"date":"YYYY-MM-DD","metrics":{...}}]}`;
  ...
}
// ai.gateway.ts:39-60  确定性抽取:response_format=json_object + temperature:0
body: JSON.stringify({ model, messages, response_format: { type: 'json_object' }, temperature: 0 }),
```

**转置表确定性解析**(`parseTransposed`,`extraction.service.ts:95-143`):经营报表是"日期作列、指标作行"的转置布局,LLM 反而易超时/解析错,故先用 **确定性规则** 解析--找日期行(Excel 序列号或日期串 ≥3 个)、按 `labelVariants`(去全角括号)多变体匹配指标列,无需 LLM;未检测到转置结构才回退 LLM。`excelSerialToISO`(`:78`)处理 Excel 序列号日期(补偿 1900 闰年 bug)。

**三触发 + SSE + 溯源**:

- **保存即抽取**(`source=save`,持锁校验,保证编辑者本人触发);
- **经理手动**(`source=manual`,manager+ 角色,免锁);
- **定时**(`node-cron` 每日 02:17,`selectDueWorkbooks` 用 `updated_at > last_extracted_at` 增量跳过,`NODE_ENV=test` 不启动);
- **SSE 逐表推送进度**(`text/event-stream` + `X-Accel-Buffering: no`);
- **三层溯源**:`workbook.last_extracted_at` / `daily_metric.last_source='ai'` / `expense.source='ai'`。

**为何新颖**:将 LLM 作为 **结构化数据入库的语义对齐层** 而非对话工具,用"表头文字语义匹配"取代"单元格坐标映射",使入库抗布局变化、跨业务可复用(同一套 prompt + `businessName` 参数适配足浴/酒店);`temperature:0` + `response_format:json_object` 趋近确定性可复现;`coerceMetric`(`validate.ts:41`)入库前清洗 `¥ , ，` 并强转,与 prompt 约束构成 **双保险**;幂等可重跑(多次抽取读同一快照、写同一 PG、最后写入胜)。

### 创新点 3:模板描述符驱动的可扩展性(JSONB)

**机制**:`template.definition` 为 JSONB,存储完整表/列描述符(`sheets[].columns[]`,含 `key/label/type/kind`);`daily_metric.metrics` 也为 JSONB(每日每店一个文档,GIN 索引)。**同一份 `template.definition` 同时驱动五个环节**:录入表结构生成、抽取解析、报表/台账生成、大屏选 metric key、AI 上下文认识新指标。

```sql
-- schema.sql:42-52  指标存 JSONB,加指标=加 JSON key,不改表不迁移
CREATE TABLE daily_metric (..., metrics JSONB NOT NULL DEFAULT '{}', UNIQUE(shop_id, date));
CREATE INDEX idx_daily_metric_metrics ON daily_metric USING GIN (metrics);
```

```ts
// footbath.template.ts:24-48  columns 数组;加指标=加一行
columns: [
  { key: 'revenue', label: '营业收入', type: 'number', kind: 'entry' },
  { key: 'customer_price', label: '客单价', type: 'number', kind: 'manual_derived' }, // 派生值,抽取时跳过
]
// extraction.service.ts:274-280  JSONB || 合并写入(经营报表+收入对账同日指标合并到同一行)
ON CONFLICT (shop_id, date) DO UPDATE SET metrics = daily_metric.metrics || $4, ...
```

**为何新颖**:`kind` 字段区分 `entry`(人工录入,参与抽取/聚合)与 `manual_derived`(人工派生值如客单价/ADR,抽取跳过),把"哪些字段自动汇总、哪些人工填"写进描述符而非代码。可扩展性场景表(spec §9):加指标/加表/加业务/大屏展示新指标/AI 认识新指标--全部"❌(不改代码)"。这是对硬约束 1 的工程兑现。

### 创新点 4:多业务泛化(businessCode 分派)

**机制**:`business` 为顶层实体,`shop`/`template` 均以 `business_id` 外键挂靠;大屏路由用 `HANDLERS: Record<businessCode, handler>` 分派表,按 `businessCode` 查找处理器(足浴/酒店),无处理器返回 501;前端 `Dashboard.vue` 用 `v-if` 分派到 `FootbathDashboard`/`HotelDashboard`。

```ts
// dashboard.routes.ts:19-22  分派表
const HANDLERS: Record<string, (p: any) => Promise<any>> = {
  footbath: computeFootbathOverview,
  hotel: computeHotelOverview,
};
// :57  缺省 businessCode=footbath(向后兼容);shopId 必须属于该业务
```

**为何新颖/可论证**:系统诚实地把"按模板自动生成大屏"列为非目标(spec `2026-07-23-大屏泛化-design.md` §2),转而采用 **手写处理器 + 手写 Vue 组件** 的线性成本策略--因为各业态指标体系差异大(足浴看钟数/客流,酒店看 ADR/OCC/REVPAR),手写保证足浴大屏零改动、新业态样板可控。这是一条值得在论文中讨论的 **工程权衡**:模板描述符驱动"录入/抽取"层(可全自动),但"大屏聚合"层因业务语义差异保留手写(确定性优先)。`business_code` 缺省足浴实现向后兼容。

### 创新点 5:大屏日期粒度聚合与 0 填充

**机制**:`granularity ∈ {day, week, month, year}`;`computeRange` 为 **纯日期数学函数(无 IO、无 `Date.now()`,便于单测)**,计算 KPI 区间与趋势窗口 + `trendUnit`;每处理器发 4 条 SQL;趋势用 `date_trunc` 桶聚合,`buildTrendSeries` 生成完整桶序列并对缺失桶 0 填充(SQL `GROUP BY` 只返回有数据行的桶,无法表达空桶)。

```ts
// dashboard.helpers.ts:35-88  computeRange(纯函数,趋势下钻:day->前14天/week->本周7天/month->当月逐日/year->12月)
// :121  0 填充:用 trendStart/trendEnd/trendUnit 生成完整桶序列,缺失桶=0
const lookup = (key: string): number => (map.has(key) ? (map.get(key) as number) : 0);
// footbath.ts:14-16  numGuard:正则护数字(非数字/空->0,避免 SUM 报错)
const numGuard = (key, prefix='metrics') =>
  `CASE WHEN ${prefix}->>'${key}' ~ '^-?[0-9]+(\\.[0-9]+)?$' THEN (${prefix}->>'${key}')::numeric ELSE 0 END`;
```

**为何新颖**:趋势下钻规则(粗粒度 -> 细粒度提供上下文)与 0 填充配合,保证大屏时间序列连续;`numGuard` 在读侧用正则兜底非数字字符串(I-1 隐患的防御层);酒店处理器的 `AVG_KEYS`(ADR/OCC/REVPAR)用 `AVG(CASE ... THEN ... END)` 仅对非 0 天求日均,避免 0 填充天拉低均值--这是"0 填充 vs 均值统计"的细节矛盾及其解法,可作论文实现细节。

### 创新点 6:AI 对话网关 function-calling(反幻觉)

**机制**:对话走 `callDoubao`(带 `tools` + `tool_choice:'auto'` + `temperature:0.3`),与抽取网关 `callDoubaoJson`(`temperature:0`)区分。LLM 不直接"背数字",而是声明意图后由服务端 `executeTool` 查真实 PG(`get_kpis`/`query_daily_metrics`/`query_expenses`/`compare_shops`/`get_template`),最多 6 轮工具循环后用中文产出经营简报(金额 ¥+千分位,末尾给建议)。

```ts
// ai.gateway.ts:73  最多 6 轮工具循环(防死循环)
for (let i = 0; i < 6; i++) {
  resp = await callDoubao(messages);
  if (!choice.tool_calls?.length) return { answer: choice.content, configured: true };
  for (const tc of choice.tool_calls) {
    const result = await executeTool(tc.function.name, JSON.parse(tc.function.arguments), ctx);
    messages.push({ role: 'tool', tool_call_id: tc.id, content: JSON.stringify(result) });
  }
}
```

**为何新颖**:用 function-calling 把 LLM 的"语言能力"与"事实数据"解耦--LLM 负责理解意图与组织语言,事实由 PG 提供,显式 systemPrompt 规则"不要编造数字"约束输出,从架构上抑制幻觉;两个网关用不同 temperature 区分"确定性抽取"与"带发散的经营建议"。

### 创新点 7:模型管理自动化

**机制**:`refreshModels` 调 Ark `GET /models` 拉取可用模型,过滤 `Shutdown`/`Retiring`,按 `task_type` 分类(`TextToImage`->image、`TextGeneration`->chat),upsert 进 `ai_model` 表;`ai_feature_config` 表按 feature(chat/poster/extraction)分配模型;`getFeatureModel` 读 DB,无行则 env 兜底(`settings.service.ts:21-26`)。

```ts
// settings.service.ts:42  task_type -> kind 分类
export function classifyKind(taskType: string[] | null | undefined): AiModelKind {
  const t = taskType || [];
  if (t.some(x => x === 'TextToImage' || x === 'ImageToImage')) return 'image';
  if (t.some(x => x === 'TextGeneration' || x === 'VisualQuestionAnswering')) return 'chat';
  return 'other';
}
// :21  查功能分配的模型;DB 无行 -> env 兜底
export async function getFeatureModel(feature: AiFeature): Promise<string> {
  const r = (await query<{ model_id: string }>(
    'SELECT model_id FROM ai_feature_config WHERE feature=$1', [feature])).rows[0];
  return r?.model_id || ENV_FALLBACK[feature];
}
```

**为何新颖**:大模型迭代频繁,手动维护模型 ID 易过期;用平台元数据(`task_type`)驱动"哪些能文生图、哪些能文本生成",功能分配由 chairman 在设置页操作,DB 持久化 + env 兜底保证向后兼容。这是一条"AI 模型治理"的工程实践。

### 创新点 8:低学习成本作为硬约束(人本设计)

**机制**:录入表直接复刻门店现用 Excel--三张表分别用"转置(日期作列/指标作行)""一行一天""一笔一行"三种布局,列名用中文行业术语(营业收入/排钟/点钟/加钟/客单价);`buildFromTemplate` 第 0 行写列名表头、预留 400 行;导入 Excel 时按模板列名校验表头,不符弹确认警告防错位;保留 Univer 原生单元格输入、Enter/Tab、公式栏。

```ts
{ key: 'clocks_arranged', label: '排钟' }, { key: 'clocks_requested', label: '点钟' }
```

**为何新颖**:把"低学习成本"提升为与可扩展性 **并列的硬约束**(spec §1.3、§12 UAT 关键验收点),并以此为依据做技术取舍--例如选 JSONB 而非 typed columns 是替员工做"不可见"的技术决策;转置经营报表改为 **自动生成只读视图**(后端从 `daily_metric`+`expense` 按日累加),员工不再维护跨表公式,杜绝 `#REF!`。这是一条 **面向终端用户接受度的人本工程原则**,可作为论文的设计哲学章节。

### 创新点 9:海报--文生图背景 + Fabric 画布分层

**机制**:服务端调 Ark `/images/generations` 文生图,取回临时 URL 转 `Buffer` 再编码为 base64 dataUrl 返回前端(避免前端跨域 Canvas 污染);前端 Fabric.js v6 在 540×960 画布上 cover 铺背景,叠加文字图层(店名/日期/自定义,带阴影),支持加企业 logo / 联系信息 / 裁剪 / 层级,导出 `toDataURL(jpeg, multiplier=2)` 出 1080×1920。

```ts
// poster.routes.ts:19-39  服务端代理取回转 base64(避免前端 Canvas taint)
const url = data.data?.[0]?.url;
const imgResp = await fetch(url);
const buf = Buffer.from(await imgResp.arrayBuffer());
const mime = imgResp.headers.get('content-type') || 'image/jpeg';
res.json({ image: `data:${mime};base64,${buf.toString('base64')}` });
```

**为何新颖**:职责分离--AI 只产背景(模型生成文字常乱码),结构化信息(店名/日期/地址电话/logo)由 Fabric 二次编辑层叠加,文字清晰可编辑;服务端 base64 代理解决 `getImageData`/`toDataURL` 的 Canvas taint SecurityError;企业 logo 落盘服务端供多门店复用。

## 六、可作为学术论文贡献的提炼

并非所有创新点都适合作为学术论文的"贡献"。按可论证性排序,建议主攻:

1. **Approach B(录入与展示分离)**--作为 SME 财务数字化的架构模式,与"电子表格即事实源"对照,论证其如何根治公式脆弱性与重复录入。**最强主贡献。**
2. **AI 语义抽取作为唯一入库路径**--将 LLM 用作结构化入库的语义对齐层(替代位置式映射),配合转置表确定性解析、`temperature:0` 确定性、双保险校验、三触发与溯源。**最具新颖性,可单独成节。**
3. **悲观锁 vs OT 的工程权衡分析**--基于"单编辑者并发"需求识别,论证弃用 OT 的合理性 + 可替换点隔离。适合作为"协同模型选择"案例。
4. **模板描述符驱动的可扩展性 + 多业务泛化的边界**--论证"录入/抽取层全自动 vs 大屏聚合层手写"的分层取舍。
5. **低学习成本作为硬约束**--人本工程原则,与可扩展性并列,以 UAT 为验收。

主题系统、模型管理、海报、bootstrap 等宜作为 **工程实现细节** 而非主贡献。
